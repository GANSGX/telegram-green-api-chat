# Архитектура и инженерные решения

## Границы задачи

Приложение реализует небольшой Telegram-клиент для одного оператора. React отвечает за интерфейс, небольшой Node.js BFF за учётные данные и интеграцию. Это решение для тестового задания и локального использования, без неподтверждённых обещаний промышленной отказоустойчивости.

```text
React UI
   │ same-origin HTTP + HttpOnly cookie
   ▼
Node.js BFF
   ├── сессия и проверка запросов
   ├── разрешение получателя
   ├── идемпотентная отправка в пределах сессии
   └── один long-poll consumer на инстанс
         │ HTTPS
         ▼
Telegram GREEN-API → Telegram
```

## Почему есть BFF

GREEN-API включает токен в URL запросов. При прямом обращении из React он присутствовал бы во всех запросах браузера и усложнял бы безопасное управление сессией. BFF изолирует URL провайдера, нормализует ошибки, контролирует одного потребителя очереди и делает собственный контракт интерфейса независимым от webhook-форматов.

Токен всё равно вводится в браузере при входе, поэтому это не защита от уже скомпрометированного клиентского устройства. Сессии размещены в памяти, секреты не сохраняются между перезапусками.

## Подключение

Сервер валидирует `apiUrl`, ID и токен. Затем параллельно читает `getStateInstance` и `getSettings`. Инстанс должен иметь `typeInstance=telegram`. До завершения проверки захватывается резервирование по ID инстанса, чтобы два одновременных подключения не запустили два потребителя.

Клиент получает только состояние подключения и случайную непрозрачную cookie. Авторизацию самого Telegram-аккаунта пользователь проходит в GREEN-API. Неготовый инстанс остаётся диагностируемым, отправка блокируется до `authorized`.

Получение событий включается отдельным действием пользователя. `setSettings` не стирает внешний `webhookUrl`. Приложение учитывает временную неготовность после изменения настроек.

## Приём сообщений

На каждый подключённый инстанс работает один последовательный цикл

1. `receiveNotification` ожидает уведомление до 25 секунд.
2. Валидное событие нормализуется и попадает в ограниченный буфер BFF.
3. `deleteNotification` подтверждает получение.
4. Следующее уведомление читается только после подтверждения предыдущего.

Повтор подтверждения отделён от получения события. Падение DELETE не вызывает повторную отправку сообщения и не дублирует событие в клиенте. Неподдерживаемые webhook-типы тоже подтверждаются, чтобы не блокировать очередь. Сообщения групп маршрутизируются по `senderData.chatId`, а не по ID автора.

React читает буфер через `GET /api/events?cursor=…`. Один инстанс не получает дополнительного upstream-poller при открытии ещё одной вкладки с общей cookie. При сетевом сбое используется ограниченный экспоненциальный backoff с jitter. AbortController завершает запросы при выходе.

Буфер содержит 512 последних событий. Устаревший курсор явно возвращает `EVENTS_EXPIRED`, клиент сообщает о возможном пропуске истории. Дедупликация и статусы учитывают chatId вместе с ID сообщения.

## Отправка

Клиент создаёт случайный `clientId` и сразу рисует сообщение со статусом отправки. BFF хранит promise запроса под этим ключом и хеширует его полезную нагрузку. Повтор того же запроса не создаёт повторного обращения к GREEN-API. Повтор ключа с другим текстом или чатом отклоняется.

После `idMessage` оптимистическая запись связывается с ID провайдера. Возможна гонка между HTTP-ответом и исходящим webhook. Модель сообщений объединяет их, сохраняя более сильный статус. Статусы, пришедшие раньше самого сообщения, удерживаются в ограниченном журнале. Запоздалый `delivered` не отменяет `read`.

У GREEN-API не задокументирован upstream-ключ идемпотентности. При сетевом обрыве после передачи запроса невозможно доказать, был ли он принят. Такое сообщение получает `unknown`, автоматический повтор запрещён. Пользователь должен проверить Telegram перед новой отправкой. Явно отклонённую отправку можно повторить вручную.

## Вложения

`POST /api/messages/media` принимает один файл до 16 МиБ и подпись до 1024 символов. Проверки сессии и Origin выполняются до multipart-парсинга. Четыре слота ограничивают одновременные загрузки, буферы не сохраняются после отправки. Хеш идемпотентности учитывает байты, имя, подпись и чат. Нативной записи голосовых нет.

BFF вызывает `sendFileByUpload`, нормализует входящие `fileMessageData` и выдаёт только `/api/media/<opaque-id>`. Ссылки провайдера хранятся в реестре текущей сессии. Разрешены только известные HTTPS-хосты и пути GREEN-API, redirects запрещены. Получение ограничено четырьмя параллельными запросами и очередью из 64 ожиданий. Лимит скачивания применяется и к потокам без Content-Length. Поддержаны HTTP Range для браузерных проигрывателей.

MIME исходящего файла проверяется по сигнатуре байтов. SVG, HTML и неизвестные типы скачиваются как документы. Для локального предпросмотра изображения ограничены JPEG, PNG, GIF, WebP и AVIF. Ответы BFF защищены `nosniff`, `Content-Disposition`, CORP и CSP sandbox. Кириллические имена сохраняются при multipart-кодировании.

React удерживает исходный File и blob-превью только в памяти страницы, освобождает URL при смене сессии или удалении из ограниченной истории. После подтверждения используется адрес BFF. Повтор явно отклонённого вложения возможен, пока исходный файл доступен; неопределённая отправка автоматически не повторяется. Скачивание после истечения серверной сессии не поддерживается.

## Состояние интерфейса

`useMessenger` объединяет сессию, последовательный polling и действия. Чистые функции доменной модели отвечают за дедупликацию, порядок статусов, историю и непрочитанные сообщения. Представление не знает URL провайдера и не разбирает webhook.

История ограничена 2000 сообщениями и 100 чатами в текущей вкладке. Черновики разделены по chatId. Повторный рендер не создаёт второй цикл polling. Смена сессии отменяет устаревшие операции. Неудачный выход оставляет доступным повтор отключения.

Состояния получения, ошибки инстанса, пустые диалоги, отправка, превышение лимита и сетевые ошибки имеют отдельное отображение. Интерфейс не придумывает online-статус собеседника, которого нет в используемом контракте.

## Модель безопасности

- Только HTTPS-хосты вида `N.api.green-api.com`, без произвольных портов, userinfo, путей и перенаправлений
- Случайная cookie, `HttpOnly`, `SameSite=Strict`, `Secure` при прямом HTTPS-запросе
- Проверки Origin, Fetch Metadata и Host, JSON для изменяющих POST-запросов, multipart только для маршрута вложений после проверки сессии
- Ограничение размера тела, количества сессий и попыток подключения
- Таймауты upstream-запросов и очищенные сообщения об ошибках
- React экранирует текст, HTML из переписки не исполняется
- Секреты не попадают в ответы, историю, Git или прикладные журналы

Процесс по умолчанию слушает только loopback. Для внешнего размещения нужны HTTPS, корректный allowlist Origin и отдельная политика доверия reverse proxy. Текущая конфигурация не доверяет произвольным proxy-заголовкам.

## Ограничения надёжности

Буфер событий, ключи идемпотентности и сессии не переживают перезапуск процесса. Если сервер подтвердил уведомление провайдеру и завершился до чтения клиентом, событие может быть потеряно для этого интерфейса. В Telegram оно остаётся. Нельзя называть это end-to-end exactly-once доставкой.

Одновременный запуск нескольких копий BFF не поддержан. Резервирование инстансов действует только внутри одного процесса. Внешние потребители той же очереди также могут забирать уведомления.

Для промышленного развития нужны долговечный журнал событий перед ACK, распределённая аренда инстанса, долговечное состояние отправок, шифрование токенов хранилища, аутентификация операторов и наблюдаемость без секретов. Эти механизмы осознанно не добавлены в небольшое тестовое задание.

## Проверка решений

Тесты проверяют контракт GREEN-API через подменённый транспорт, реальные локальные HTTP-маршруты BFF и чистую модель клиента. Критичные сценарии включают чужой Origin, запрещённый хост, неправильный тип инстанса, конкурирующие подключения, идемпотентность, неопределённую отправку, повтор ACK, дедупликацию и перестановку статусов.
